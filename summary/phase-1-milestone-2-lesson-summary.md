# Phase 1 — Multi-Tenant Security in Cosmos DB: Milestone 2 Lesson Summary

**Status:** Milestone 2 (Isolation Enforcement at the Code Layer) complete. Milestones 3–5 of Phase 1 not yet started.
**Focus:** Deriving `tenantId` exclusively from a validated JWT, enforcing it as the single source of truth across every layer, and making it structurally hard (not just conventional) for a developer to bypass.

---

## What Was Done

- **JWT authentication wired up** via `AddAuthentication().AddJwtBearer(...)`, with an explicit `TokenValidationParameters` block (`ValidateIssuer`, `ValidateAudience`, `ValidateLifetime`, `ValidateIssuerSigningKey`, symmetric `IssuerSigningKey` from config) — chosen over `Authority`-based auto-discovery since tokens are self-issued for this exercise, not minted by an external identity provider.
- **`TenantContext` split across two interfaces** resolving to the same scoped instance:
  - `ITenantContext` (read-only, `GetTenantId()`) — injected wherever tenant scoping is needed for reads/writes.
  - `ISettableTenantContext` (`SetTenantId(string)`, write-once — throws if called twice) — injected only by the middleware.
  - Registered as `AddScoped<TenantContext>()` once, with both interfaces resolving via `provider.GetRequiredService<TenantContext>()` factory delegates, so a single scoped instance backs both faces.
- **`TenantMiddleware`** (convention-based, not `IMiddleware`) extracts the `tenant_id` claim from `context.User`, rejects (missing claim → logged error + exception; invalid signature → flagged as a potential attack) unless the matched endpoint carries `[AllowAnonymous]` metadata (checked via `context.GetEndpoint()?.Metadata`), in which case tenant enforcement is skipped entirely.
- **Pipeline order settled:** `UseRouting → UseAuthentication → UseAuthorization → TenantMiddleware → MapControllers` — routing before authorization (endpoint metadata needed for policy checks), authentication before the tenant middleware (claims need to exist), authorization before the tenant middleware (no point extracting tenant context for a request about to be rejected anyway), tenant middleware before the actual handler runs.
- **`CosmosClient` removed from DI entirely.** Built once as a local variable in `Program.cs` (composition root), captured by closure inside the `AddScoped<ITenantDataAdapter>` factory delegate — no `CosmosClient` registration exists anywhere in the container, so no other class in the codebase can inject it directly.
- **Admin routes** carry `tenantId` as an explicit request parameter (not a personal claim), gated separately by role-based authorization (`[Authorize(Roles = "Admin")]`) — kept deliberately distinct from tenant isolation as a separate concern.
- **DTO boundary enforced:** `NewVehicleRequest` DTO excludes `Id` and `TenantId` entirely from user input; business logic layer (which depends on `ITenantContext`) owns converting the DTO into a complete domain `Vehicle`, since domain-object completeness is a business-rule concern, not a persistence concern.
- **Zero-trust re-derivation at the data layer:** even though business logic already sets `TenantId` correctly on the domain object, `TenantDataAdapter` independently re-pulls `TenantId` from its own injected `ITenantContext` for query/partition-key construction rather than trusting the value already on the object — defense against a hypothetical bug anywhere upstream.
- **Dev-only JWT-issuing endpoint** built to generate test tokens, reading the same `Jwt:Key`/`Issuer`/`Audience` from `IConfiguration` that the validation pipeline checks against (so there's no separate hardcoded secret to drift out of sync), gated behind an existing custom "Development-only" attribute (404s outside Development).
- **Two-directional isolation proof actually run and confirmed:** a JWT for `tenant-a` writing a vehicle with a spoofed `tenantId: tenant-005` in the request body was ignored — the record was created under `tenant-a` (the JWT's tenant) regardless. A point read for that same vehicle using a different tenant's JWT returned nothing.

---

## Key Decision: `ITenantContext` as the Single Source of Truth

**Final rule, stated the way it should be defended in an interview:** *No layer trusts a `tenantId` that arrived any way other than through `ITenantContext`, which traces back to a single validated JWT claim, set exactly once per request by trusted middleware. Not from a request parameter, not from a field already sitting on a domain object, not from anywhere else — even when that other source happens to be correct.*

**Reasoning:** Even though business logic correctly sets `TenantId` on the domain object before handing it to the data adapter, the data adapter re-derives it independently from its own `ITenantContext` rather than reading `vehicle.TenantId`. This isn't solving a known bug — it's adopting a zero-trust stance at every layer as insurance against an *unknown* future one, on the theory that a single, well-secured source of truth (JWT validation is standard library code, not custom and bug-prone) is safer to depend on repeatedly than trusting values as they pass hand-to-hand through the call stack.

## Notable Moments / Weak Spots to Revisit

- **Reassignment vs. mutation — the core conceptual bug of this milestone.** First working draft of the middleware read:
  ```csharp
  else { tenantContext = new TenantContext(tenantId); }
  ```
  This compiles, appears to work in isolation, and does nothing: `tenantContext` is a local parameter reference to an object the DI container already resolved (call it Object A). Reassigning the local variable points it at a brand-new, unrelated object (Object B) that nothing else in the request ever sees; Object B is discarded the moment the method returns, and every other class resolving `ITenantContext`/`ISettableTenantContext` later in the same request still sees the original, unmodified Object A. This was walked through concretely as a memory-address trace (`0x1000` untouched, `0x2000` allocated and immediately unreachable) rather than accepted at the analogy level, since an earlier "sticky note" framing was initially misread as "the object gets overwritten" rather than "the label gets repointed."
  - **Fix:** mutate the existing object via a method (`tenantContext.SetTenantId(tenantId)`), never reassign the parameter.
  - **Second-order design consequence:** this is precisely why `ISettableTenantContext` needed a **method**, not a settable property — a method makes "mutate the existing instance" the only available shape; a public setter would have permitted the exact same reassignment mistake to resurface at the call site instead of inside the class.
- **Two near-miss singleton mistakes, same underlying confusion, caught before either shipped:**
  1. First instinct on hitting the "no suitable constructor" DI error for `TenantMiddleware` was to try registering it as a singleton service — a dead end, since convention-based middleware (`app.UseMiddleware<T>()`) is never registered in the DI container at all; the framework activates it directly via `ActivatorUtilities`.
  2. Separately, an early proposal for wiring `ISettableTenantContext`/`ITenantContext` to "the same instance" involved closing over one `var tenantContext = new TenantContext()` built once in `Program.cs` — correctly self-caught before implementing, by reasoning through what happens to two *concurrent* requests (Tenant A and Tenant B) sharing one closed-over instance. The closure pattern that correctly solved the `CosmosClient` problem (one instance, safe to share forever) does not transfer to per-request state — the actual fix was registering the **concrete class** `TenantContext` as `AddScoped`, then having both interface registrations resolve it via `provider.GetRequiredService<TenantContext>()`, so "same instance" is guaranteed per-request by the container, not manufactured by a closure.
  - **Process lesson:** "same instance across two registrations" and "one instance for the whole app" sound similar but are solved by opposite mechanisms (scoped DI resolution vs. closure-over-a-singleton-value) — worth having a crisp trigger question ready ("does this value need to be one-per-app or one-per-request?") before reaching for either pattern again.
- **Constructor vs. `InvokeAsync` parameter placement for convention-based middleware — a real runtime error, correctly self-diagnosed from the stack trace.** Initial middleware had `ILogger` on the constructor and both `RequestDelegate next` and `ISettableTenantContext tenantContext` on `InvokeAsync`. App failed to start: `"A suitable constructor for type 'TenantMiddleware' could not be located."` Root cause found by reading the stack trace closely — `ReflectionMiddlewareBinder.CreateMiddleware(RequestDelegate next)` revealed the framework was trying to hand `next` to the constructor, not `InvokeAsync`.
  - **Corrected, defend-it-ready rule:** constructor parameters for convention-based middleware are resolved **once, at pipeline-build time** — appropriate for values that never change per request (`next`, singleton services). Method parameters on `InvokeAsync` are resolved **fresh, per request** — required for anything scoped (`ISettableTenantContext`). Putting a scoped dependency on the constructor would silently freeze it at whatever value existed the first time the pipeline was built — the same category of bug as the `CosmosClient` closure mistake above, just manifesting as stale data instead of a startup crash.
- **Double base64-encoding the JWT before pasting into Postman — a self-diagnosed tooling error.** Symptom: `TenantMiddleware` consistently saw `context.User.IsAuthenticated == false` and no `tenant_id` claim, despite a correctly-issued token and correctly-configured validation. Correctly narrowed to "the token itself" rather than "the validation config" by checking the raw string's shape — a JWT is already a complete, base64url-encoded, dot-separated compact token (`WriteToken(...)` produces the final form); encoding it a second time collapses the three segments into one indistinguishable blob, which the bearer handler can't parse as a token at all, so it silently treats the request as unauthenticated rather than erroring loudly.
- **`[AllowAnonymous]`-decorated dev endpoint still failing tenant middleware — correctly reasoned through, not just patched.** Initial confusion: "shouldn't `UseAuthorization()` have already stopped this?" Resolved by distinguishing what `[AllowAnonymous]` actually does — it tells `UseAuthorization()` "no policy required," which lets an *unauthenticated* request pass through successfully (not "reject unauthenticated users"), so it continues downstream into `TenantMiddleware` exactly as an anonymous request. Considered and rejected two alternative fixes before landing on the right one:
  - A bespoke tenant-exemption attribute/whitelist — rejected as introducing a second, lower-stakes convention that's easier to forget.
  - Conditional pipeline branching via `MapWhen`/path-string matching — rejected for the same reason (route strings drift, nobody's specifically watching them).
  - **Landed on:** checking `context.GetEndpoint()?.Metadata` for `AllowAnonymousAttribute` directly, reusing an attribute developers are already under strong, pre-existing pressure to apply correctly (getting it wrong leaves an endpoint completely unsecured, a much bigger and more visible risk than a tenant-scoping gap) rather than inventing a new low-visibility rule.

## Carried Forward Into Milestone 3

- Tenant isolation is enforced in application code end-to-end: middleware → scoped `TenantContext` → business logic → data adapter, proven with an actual two-directional spoofing test (write with a mismatched body `tenantId`, cross-tenant read), both correctly blocked.
- **Fail-closed design confirmed as the real second line of defense**, not query/partition-key discipline: if the middleware were ever left unregistered, `TenantContext.GetTenantId()` throws `InvalidOperationException` the instant the data adapter needs it — the system fails loudly and immediately rather than leaking quietly. Milestone 3 (RBAC / resource tokens) is explicitly a *third*, platform-level line of defense on top of this, not a replacement for it.
- `CosmosClient` is unreachable outside `TenantDataAdapter` via DI-registration removal + closure — flagged in-conversation as sufficient for this milestone, with true assembly-level enforcement (making `CosmosClient` construction physically unreachable via `internal` visibility across an assembly boundary) explicitly named as a stronger, deferred hardening step that belongs with Milestone 3's platform-layer defense-in-depth theme, not built now.
- Admin-route design (`tenantId` as an explicit parameter, gated by role claim rather than tenant claim) is in place but not yet paired with actual RBAC enforcement — that pairing is Milestone 3's job.
- Weak-spot flagged for a second rep: the **constructor-vs-method parameter distinction for convention-based middleware** and the **closure-vs-scoped-DI-resolution distinction** both required more than a rung-2 hint to land — worth being able to state both rules cold, unprompted, before Phase 1 is considered closed.

## Addendum — Fallback Authorization Policy (discovered post-checkpoint, folded back in)

**Trigger:** while manually testing `TenantMiddleware`, an expired JWT was expected to be rejected by authentication before ever reaching the middleware. Instead, the request reached `TenantMiddleware` and failed there with the custom "Tenant context is not available" error — an unexpected, not-obviously-wrong-looking result that turned out to be a real gap, not a red herring.

- **Root cause, correctly isolated step by step rather than patched on a guess:** the endpoint under test had **no `[Authorize]` attribute at all**. `UseAuthentication()` correctly failed to validate the expired token (confirmed directly from Serilog output — `SecurityTokenExpiredException`, "Bearer was not authenticated") and left `context.User` as an empty, unauthenticated `ClaimsPrincipal`. `UseAuthorization()` only *rejects* a request if the matched endpoint has an explicit requirement; with no `[Authorize]` present, an unauthenticated principal was allowed through by default, straight into `TenantMiddleware` — which correctly caught the missing `tenant_id` claim, but only as an incidental side effect, not as its intended job.
- **Two false leads chased and correctly ruled out before finding the real cause** — a useful pattern to notice, not just the destination:
  1. **Clock skew** — hypothesized first, since `JwtBearerHandler` tolerates tokens up to 5 minutes past `exp` by default. Ruled out by checking the actual log timestamps: the token was over three hours expired, far outside tolerance.
  2. **A missing/misconfigured `Events` handler** silently swallowing the 401 — ruled out by reviewing `ConfigureAuthentication` directly and confirming no `OnAuthenticationFailed`/`OnChallenge` handlers were registered at all.
  3. **The actual cause** — attempted to add `[Authorize]` to "the endpoint," tested, saw no change, and initially concluded the attribute wasn't taking effect. Root cause of *that* red herring: the attribute had been added to a similarly-named but different endpoint than the one actually under test. Caught only by explicitly re-verifying the exact route being hit rather than trusting memory of having already checked it — the same category of self-correction as the tenant-ID mix-up during Milestone 1's RU testing.
- **Fix — global fallback authorization policy**, not a per-endpoint attribute reminder:
  ```csharp
  builder.Services.AddAuthorizationBuilder()
      .SetFallbackPolicy(new AuthorizationPolicyBuilder()
          .RequireAuthenticatedUser()
          .Build());
  ```
  This requires authentication on **any endpoint with no explicit `[Authorize]`/`[AllowAnonymous]` metadata at all**, closing the "developer forgot the attribute" gap by default rather than relying on convention — the same category of fail-open risk already reasoned through for `CosmosClient` and the data adapter earlier in this milestone, just one layer up in the pipeline.
- **Confirmed `[AllowAnonymous]` and `[Authorize]` both still take precedence over `FallbackPolicy`** — the fallback only applies when an endpoint declares neither, so `TenantMiddleware`'s existing `AllowAnonymousAttribute` metadata check (used to exempt the dev-token-issuing endpoint) needed no changes and continues to work unmodified alongside the new global policy.
- **Confirmed `TenantMiddleware`'s own missing-claim check remains non-redundant even with the fallback policy in place** — the fallback policy only guarantees a request has *some* validly-authenticated identity; it says nothing about whether that identity's token happens to carry a `tenant_id` claim. A validly-authenticated user with no tenant claim is still a distinct failure mode `TenantMiddleware` alone catches.
- **Personal, lived justification for choosing the global policy over "remember `[Authorize]` on every endpoint":** the gap was found by *personally forgetting the attribute on the very endpoint being used to test this exact scenario*, moments after having reasoned through why relying on that convention was risky. Worth keeping as the concrete story for "why not just use `[Authorize]` everywhere" if an interviewer pushes on it — it's a real anecdote, not a hypothetical.
